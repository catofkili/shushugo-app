# 每日时间预算排法（2026-11-03 设计；先只在模拟器里验证，不接 App）

## 0. 为什么要改

作者 11-02 的要求（原话整理）：

- 混合模式改成「用户自己挑哪几种题进来」（「点菜」只是比喻，**不做菜单界面**），提供一键建议；
  和圆环（四种题的每日量）合并成一处；**始终有一键安排，默认半自动：用户自己设的数优先级最高，其余自动调整**。
- 调整算法一定要跑模拟，按不同学习情况做，**尤其看阶段交接**（比如 N3 学完之后学什么）。
  作者本人就是典型：单词 N3 学完往 N2，语法回头看 N4。**模拟的时候不能把人当机器。**

人设基线（`docs/audits/2026-11-02-persona-load-baseline.md`，跑在 6eeffad8，**早于 09e67d8e 的「复习上限跟着人走」**）的结论：

1. **排法没有「今天有多少时间」这个概念。** 复习上限和新学额度是固定数，不随当天能学多久收缩。
   上班族（工作日 15 分钟）单日应做 = 可用时间的 2.1 倍（最差 2.4），断两周再回来 2.3（2.9），吃力的人 1.5（2.3）；
   模拟人在超负荷后更容易缺课，上班族 90 天里因此多缺 5.5 天（最差 8 天）。
2. **阶段交接会冲高**：交接后两周最重一天 ÷ 交接前一周中位数，单词 1.0–1.5（最差约 2.0），语法 1.4–1.5（最差 2.1–2.7）；
   交接后有 1–6 天「计划说继续，实际新学为 0」。
3. 时间充裕的人（作者本人、冲刺、轻量）没有超载。

## 2. 算法：每天早上滚动重算一次

### 2.1 输入

- **预算 B（分钟 / 天）**
  - 用户设了就用用户的（钉住）。
  - 没设：**跟着人走**。取近 14 个**有学**的日子每天实际答题量 × 固定秒数的**中位数**（和 `review-budget.ts` 的 ⓪ 同口径：
    用中位数，爆量那一天不能把之后两周带偏）。
  - 只看「做了多少」会被自己的安排卡死：排得少 → 做得少 → 预算更少。所以加一条**试探**：近 7 个有学的日子里有 ≥ 4 天把当天清单做完了，
    B 可以比中位数上调 10%（`BUDGET_GROWTH = 1.1`）。没做完的日子多，就老实按中位数。
  - 没有历史（新用户、前几天）：用备考计划 / 强度档折出来的分钟数；都没有就 20 分钟。
- **今天必做**：四种题各自今天到期的复习（受现有上限 `planReviewLimit` / 单词自动档约束）+ 今天放行的先验（`prior-pacing.ts`）+ 顽固词闸。
- **往后 H = 28 天的预测**：
  - 已有卡：按 `fsrs_due` 数每天到期多少（只数第一次到期，复习后再到期的不算 —— 低估，靠新学那条曲线兜着，写进局限）。
  - 先验：`forecastPriorReleases`（已有）。
  - 新学：每天新学 n 张，之后每周平均再答几次，沿用 `plan/load-model.ts` 的 `ANSWERS_BY_AGE_WEEK`（3, 2, 1.5, 1.5, 0.5…）。
- **需要量**：每种题按备考计划摊到每天该学多少（现成的 `dailyPlanView().segments[].suggest.fresh` / `previewCurrentLevelPlan`），
  加上「允许范围里还剩多少没学的」（含 95% 提示选了往上 / 回补之后打开的级别；选了「先不加」的那一类需要量为 0）。
- **钉住的数**：用户设过的某类新学 / 复习上限，原样用，不参与缩放。

### 2.2 分配

1. 必做 M0 = 今天必做 × 秒数。
2. **M0 ≥ B**（复习就塞满了，常见于断档回来、时间很少的人）：没钉住的新学全部为 0；
   复习总量收到 B × 1.2 以内，装不下的部分**不丢**，第二天仍是到期（谁先出由现有的随机抽 / 将来的保护档决定，这里只管「给几张」）。
   用户钉住的复习上限照用，哪怕超过 B。
3. **M0 < B**：没钉住的几类新学量 = 需要量 × 同一个系数 x。x 取**最大**的那个值，使得往后 28 天**每一天**的预测用时都 ≤ B
   （二分查找；卡的是整段峰值，不是某一周 —— 新学的复习最密的是头两周）。x 上限为 1.5（时间多也不超过需要量的 1.5 倍）。
4. **平滑**：每类新学量和昨天比，变化不超过 ±30%（至少允许变 2 张），免得今天 0、明天 30 来回跳。
5. 某一类没内容可学了（这一级学完、选了「先不加」）：需要量 = 0，它腾出来的时间自然流给其它没钉住的类；只在各自需要量 × 1.5 以内。

一键安排 = 清掉所有钉住，按上面重算并应用。默认每天早上自动重算没钉住的几类（半自动）。

### 2.3 阶段交接为什么能平

窗口 28 天能提前看到「这一类还有 9 天就学完」。学完前按作者选的方向（往上 / 回补 / 先不加）把后面的需要量算进去，
所以交接那天不会突然空掉，也不会因为下一级打开、先验整批进池而冲高（先验仍按限速放，计入必做）。

### 2.4 混合出卡顺序

现在是「每 5 个单词插一张别的」（`mixed-session.ts` 的 `MIXED_EVERY`）。改成**按完成比例最落后的那类先出**：
下一张 = 当天「已做 ÷ 计划」最小的那一类（并列按 单词 → 语法 → 汉字 → 辨析）。
时间用完时四类做完的比例差不多，不会出现「单词做完了，语法一条没碰」。

## 5. 实现说明（模拟器阶段）

### 5.1 纯函数与逐日预测

新增 `frontend/src/lib/plan/budget-allocator.ts`，仅模拟器运行时引用；不接入 App，不新增生产模块的 export。
实际签名如下（`PlanKind` 为 words / grammar / kanji / confusion）：

```ts
interface BudgetInput {
  budgetMinutes: number;
  seconds: Record<PlanKind, number>;
  mandatoryToday: Record<PlanKind, number>;
  dueForecast: Record<PlanKind, number[]>;
  priorForecast: Record<PlanKind, number[]>;
  need: Record<PlanKind, number>;
  contentLeft: Record<PlanKind, number>;
  locked: Partial<Record<PlanKind, { fresh?: number; review?: number }>>;
  previousFresh?: Record<PlanKind, number>;
  horizonDays?: number;
  uncappedToday?: Record<PlanKind, number>;
}
interface BudgetOutput {
  fresh: Record<PlanKind, number>;
  reviewLimit: Record<PlanKind, number | null>;
  peakMinutes: number;
  scale: number;
  overloaded: boolean;
}
allocateDay(input: BudgetInput): BudgetOutput;
inferBudgetMinutes(input: {
  history: { minutes: number; completed: boolean }[]; // 从旧到新
  budgetMinutes?: number; // 显式预算优先
  fallbackMinutes?: number;
}): number;
```

`dueForecast`、`priorForecast` 下标0指明天；另外检查今天必做加新学，因此默认实际检查今天及之后28天。
采用 `load-model.ts` 的3、2、1.5、1.5、0.5…周答题曲线。该常量没有导出，模拟器新增的纯函数保留同值，
不为实验改动生产导出。逐日展开明确采用：首次当天一次、首周剩余两次摊到后六天，之后每周次数均分七天；
每一天新增一批，最后一批按剩余内容截断，耗尽后停止投放。这是周模型展开到日模型所需的明确近似，
不是新的FSRS调度。二分找共同系数，按张数向下取整；不靠整分钟四舍五入掩盖峰值。

有限剩余内容会破坏二分所需的单调性：较大的新学额度提早学完，可能刚好避开第28天的既有卡峰值。
因此二分后还从高到低检查整数额度发生变化的区间；枚举上界同时受内容、需要量×1.5和今天预算约束，
不枚举任意小数。单测包含「剩10张、第28天到期7张、B=8分钟、每张1分钟」的反例：只二分会分0张，
实际分8张能安全提早结束。这是相比设计稿「只二分」增加的必要校正。

硬约束优先顺序为锁定、暂停/无内容、预算和需要量×1.5上限、平滑。若昨日额度的平滑下限本身会突破预算，
允许更快下降；上调仍限制在30%或至少2张以内。常规可行输入的预测每天≤B；若既有卡/先验或钉住的新学本身
已经让未来某一天超过B，则不能通过缩放新学消除，输出0个可变新学并如实标记 `overloaded`，不删除预测量。
这是不可行输入的报告边界，不是放宽预算来过验收线。

`uncappedToday` 是相比建议形状增加的数字输入：先验验证、减负、压轴不占普通复习cap，过载时先预留它们，
再按同一比例缩普通复习；钉住的复习不缩。它们或锁定量已超过B×1.2时无法强保上限，仍照实记录。
`reviewLimit` 非过载时未锁定类均为null；锁定类原样返回，但调用方始终不写这些字段。

### 5.2 应用可见输入、只读SQL与写回边界

输入集中在 `persona-sim/budget-policy.ts`，其入口只有锁定状态、过往逐日完成情况和原始计划/强度偏好，
没有 `Persona`、标定系数、缺席率或基准分钟参数。`inferBudgetMinutes` 和 `allocateDay` 也不读取这些模拟人参数。
用于比较的真实可用时间与B是两条独立路径；报告才用人设基准计算B/基准。

- 今日必做直接读 `dailyPlanView` 的复习段，继承单词自动档、`planReviewLimit`、顽固词闸和先验限速。
  减负/压轴先通过既有入口准备，计入必做及不可裁减部分。
- 未来先验使用 `forecastPriorReleases`，查询包括今天再切去今天，避免把今天将放行的一批又算成明天放行。
  未来R/答对率未知，仍沿用当日先验额度，绝不加快self的N4语法先验。
- 没有现成的「四类逐日首次到期数组」接口，按既有 `PRIOR_ENTITIES` / FSRS实体资格、`fsrs_due` 和
  `pendingPriorSql` 做只读SQL；不新增export。既有卡只计首次到期，后续再到期不模拟，仍有低估风险；
  汉字/辨析未来查询没有复刻私有题面资格筛选，可能保守高估，晨间必做/内容剩余和实际出卡仍走正式池子。
- 四类全部作答次数（包括重学）按固定秒数汇总最近14个有学日；没有读取历史用时表。既有历史没有保存完整
  当日清单，无法可靠反推是否做完，标为未确认；模拟开始后使用观测到的日终剩余、减负/压轴及五十音完成状态。
  试探加10%只使用确实观测到的完成日，不把「今天有答题」等同于「完成清单」。无历史时用初始备考/强度
  新学量乘固定秒数，均为0时回退20分钟；初始基线不随预算写回递归缩小。
- 需要量沿用圆环建议，并把实际允许范围的剩余内容除以计划进新窗口。单词使用 `remainingPlanWords` 和
  `levelAdvanceTarget`；语法在 `scopeLevels(PLAN_GRAMMAR_LEVEL)` 内用同等只读SQL数未学条目；
  汉字/辨析沿用正式pool。已选往上开放的级别一起参与，回补级在允许范围内；有效「先不加」及五十音门槛令
  对应需要量为0。无考期则用初始强度额度；考期进新窗口结束后不再自动添新。
- 当前App尚无独立持久「钉住」标记，不能把备考预设产生的每个额度冒认成手动锁。实验以人设显式
  `locked` 表达用户选择；新增 `cram-lock` 仅钉住单词新学40，两个排法都保存40。它与cram复用相同随机流。

**写回路径与§3原示意不同**：预算排法不调用 `saveDailyPlan`。圆环0/0段的 `keepOr` 会先写关闭哨兵，
即使那段根本没动；这个生产bug留给另一任务。这里仅用
`saveStudyPreferences({...getStudyPreferences(), ...patch})` 写未锁定的四类新学字段，只有过载时才可写
未锁定的普通复习cap；其它偏好逐字段断言写前写后相等，锁定字段额外断言。非过载日不会自动恢复前一天写下的cap，
因为那同样属于未分配字段，实验遵守本任务的写回约束。

生产偏好仍有原生额度范围：单词/汉字最多50、语法30、辨析20；输出同时记录请求的 `fresh` 和实际保存的
`appliedFresh`，次日平滑用后者。单词cap的0表示自动、-1表示不限，无法表达「关闭普通复习」，过载分到0时
只能写最低1；另三类0张用 `PLAN_REVIEW_DISABLED`。这些都不通过改生产代码绕开。

准备减负/压轴会调用 `ensureStage1Tasks` 提前物化旧单词清单；仅保存偏好不会重抽普通复习。
预算写回后必须在stage1阶段调用既有 `refreshTodayWordPlan`，否则当天仍可能沿用旧cap。
每日另断言真实普通复习清单不超过新cap；只重排内存模拟库，current路径不增加重排。
系统固定搭配仍按既有独立每日3张规则投放，不占普通单词dailyGoal；本实验没有为这批额外新卡单建预测曲线，
实际应做分钟会计入它们，不能把纯函数预测峰值等同于真实整场上限。

混合顺序仅在模拟器按正式进度的「完成/晨间计划」从小到大选，平手按单词、语法、汉字、辨析；
候选仍通过stage1和三类既有会话取，评分仍走正式入口，`mixed-session.ts` 不改。减负和压轴仍走既有独立前后段。
默认current继续走原先每5词插卡路径。M5新增锁定值在存值或生效层被改的天数；M2保留原始零新学指标，
另存验收用的 `continuingNoFreshDays`，包含预算暂时分到0但仍有需要量的日子，排除用户选择暂停的交接事件。

### 5.3 运行、缓存、标定与对比

`PERSONA_SIM_POLICY=current|budget` 默认current；`PERSONA_SIM_OUTPUT` 必须为绝对路径，指定时就是最终输出目录。
不指定时保留 `frontend/.local/persona-sim`，smoke仍用其 `smoke/`。不同排法请分别指定目录。
缓存保存共同源码指纹 `sourceHash` 和加入policy后的 `simulationHash`，两种排法不能复用分片；`cram` 分片也不能
误收 `cram-lock` 的同前缀文件。原有IDS、SEEDS、RANGE、PARALLEL及CHILD_TIMEOUT_MS继续有效。
