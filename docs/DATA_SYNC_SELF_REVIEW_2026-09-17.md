## 未通过的验收

### P1：多标签页仍可覆盖学习增量

位置：`frontend/src/lib/storage.ts:777`，实际增量写入在 803 行。

新加的 Web Lock 只包住完整快照保存；常规 `persistNowInQueue` 直接写共享的 `study-database-delta`，没有跨标签锁、版本检测或合并。两个已启动标签各答一题再交替保存，第二个增量会替换第一个。两份独立 storage 模块共享 IndexedDB 替身和 Web Locks 的检查中，锁调用次数为 0，持久化答案只有 `[2]`，预期为 `[1,2]`。

这验证了真实 storage 调度路径的遗漏，浏览器 IO 与增量内容为可控替身，不是 Chrome 双标签真机验收。另经代码检查，整库保存遇到 `loadedBrowserRevision === null` 会跳过合并，且只读取完整快照、不读取对方增量，也仍需处理。不能仅在现有增量写入外再包一把锁就称为修好。

### P1：小程序接受旧快照后退回较旧的学习状态

位置：`wechat-miniprogram/src/runtime/sync-snapshot.js:467`。

小程序本地业务表没有 `sync_updated_at`；导出快照才补该列。新增规则拿本地空版本与远端非空版本比较，因此旧远端也会胜出。实际调用小程序当前导出器和合并器：本地 2030-01-02 已学 9 次，远端 2030-01-01 仅学 1 次，合并后变为 1 次。

必须统一“本地写入、接收远端、再次导出”的版本持久化规则，并同时检查新覆盖旧、旧不覆盖新、重复合并及本地后续编辑。上一轮只验证远端较新的单向用例，漏掉了相反方向。

### P1：Web 拒绝当前小程序正常导出的快照

位置：`frontend/src/lib/sync/merge.ts:91`。

把当前小程序实际 `exportSyncSnapshot()` 输出直接交给 Web `mergeDatabaseBytes()`，立即报错：无法保留 `direction_tasks, achievement_unlocked`。这两张表属于现有小程序版本，不是假设中的未来字段。

拒绝未知数据确实避免了静默删表，但同时中断了现有跨端同步。应明确保留/映射这些平台表的方案；不能只把它们加入允许清单后继续丢弃，否则又回到原始数据损失问题。

### P1：已有游客学习记录无法首次绑定云账号

位置：`frontend/src/lib/sync-api.ts:756`。

没有 owner、已有学习记录时，新增 guard 会拒绝手动上传。自动同步让用户去设置选择上传/拉取，但手动两条路径又调用同一个 guard，没有实际完成首次绑定的入口。

合成新账号与本地游客记录，调用真实 `pushCloudBackup()`，在任何网络请求前就被拒绝。跨账号阻断本身通过了检查；首次绑定流程没有完成，不能以要求用户清空既有记录来替代。

### P2：小程序语法“取消永久掌握”仍不生效

位置：`wechat-miniprogram/src/runtime/sync-snapshot.js:640`。

语法分支先用 `targetColumns` 丢弃本地没有的版本列，再调用新合并函数，因此版本分支实际没有收到远端版本，仍落到旧的 MAX 规则。实际快照中较新的 `known_forever=0` 合并后仍为 1。

应把版本信息带到比较过程，并保存原版本供下一次合并；仅给函数增加新分支不代表调用链已经使用它。

### P2：学习时长明细清空后，汇总仍保留旧值

位置：`frontend/src/lib/sync/study-time.ts:104`，启动恢复新增调用位于 `storage.ts:319`。

原审查要求同时处理更新和“日期已经没有任何明细”。上一轮只增加了调用，汇总函数仍只 upsert。实测某日 60 秒明细删除后再重建，汇总依旧是 60 秒，预期为 0 或无该日期行。

这属于原要求未完成，不能称为本次新引入的缺陷。修正时还要区分历史时长迁移与真正删除，避免把旧汇总重新回填成已删除的明细。
