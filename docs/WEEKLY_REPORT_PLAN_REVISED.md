> 首次核对：2026-09-11；2026-09-12 更新：基础周报闭环已按第 13–15 节落地。前面的风险分析保留为审查记录，仍需按发布闸门完成真机、生产云端和商业流程验收。
> 配套规则：[设计规格修订版](./WEEKLY_REPORT_DESIGN_REVISED.md)。原稿保留：[开发规划](./WEEKLY_REPORT_PLAN.md)、[设计规格](./WEEKLY_REPORT_DESIGN.md)。
> 本文件依据当前工作区源码和隔离检查；未核验生产环境、真实账号、远程数据库、推送真机或付费商业链路。

## 1. 原规划最需要纠正的地方

原规划列出了功能，但没有把“什么数据算一份周报”“内容何时固定”“本地未上传记录怎样补齐”“通知怎么知道有周报”等问题变成可执行规则。直接沿用原顺序，可能先做完存储、手势和动效，最后才发现历史数据与触达无法满足设计。

优先级应改为：**产品口径 → 历史准确性与完整内容组装 → 可靠本地快照 → 可点击的阅读闭环 → 手势与动效 → 通知/分享 → 云端权益**。云端存储不应阻塞离线阅读价值的验证。

| 优先级 | 已发现的问题 | 修改方向 |
|---|---|---|
| P0 | “没有周报代码”与“数据层已完成”并存 | 审查时页面尚未接入；当前基础页面、快照和通知闭环已接入，发布环境闸门仍未替代 |
| P0 | 旧周报引用今天的连续天数和当前累计 | 全部历史指标截至窗口末日；补测跨周、回看与补算 |
| P0 | 新用户滚动平均注释与代码不符 | 区分使用前不存在的周和使用后的真实零新增周 |
| P0 | 新表建好不等于增量保存、恢复和同步已覆盖 | 追踪本地 delta、整库、云导出与旧客户端路径 |
| P0 | 生成、外部通知、轻用户门槛没有闭环 | 采用配套设计的时间与状态表，先完成站内闭环 |
| P1 | P4 高光、P5 选词、类别轮换仍缺实现 | 作为完整报告组装的明确交付物 |
| P1 | “只夸不贬”被用于维持失真的预测 | 停用未经证实的人群对标与单向 ETA |
| P1 | 历史付费范围、删号、断订没有定义 | 本机已有历史可读；云端生命周期另设上线闸门 |
| P1 | 成本计算混用资格率、付费率、索引行数 | 用同一公式重算，包含请求与峰值 |
| P2 | 复杂手势与五套动效库提前成为核心路径 | 先完成按钮操作与静态排版，再测手势和动效 |

### 2.2 修复前的三个已隔离复现缺口

使用临时目录中的 Vitest + 内存 SQLite，调用当前 `weekly.ts`，仅替换数据库入口与测试时钟；未读取真实学习库。三个复现断言都确认了下列现有行为，**这些通过的断言是在证明缺口存在，不是修复后的回归通过**。

1. **历史连续天数读今天。** 构造截至 2026-09-12 连续 14 天打卡，时钟设为 9 月 13 日且当天未打卡，读取 9 月 6–12 日周报，`streak` 为 0。根因：`getStreak()` 使用 `studyDate()`，不接收窗口终点。
2. **旧周累计混入未来。** 9 月 7 日和 9 月 20 日各一条打卡、两词当前 `seen_count > 0`，读取 9 月 6–12 日周报，累计天数、词数都返回 2。根因：`checkins` 无窗口上界，词数直接读取当前 `progress`。
3. **新用户第一周速度被稀释。** 仅 9 月 7 日首次作答 4 个词，`getRollingSpeed()` 返回 1。根因：循环四次都增加分母，未实现注释中的“数据不足按实际周数”。

另有两项审查发现：既有“时长跨设备”测试把 `word_study_time` 建成了带 `device_id` 的明细表，与真实架构不同；既有“铁人”测试直接把 `m.streak` 改成 20，无法验证真实历史连续计算。这不说明所有现有测试无用，而是需要补齐生产形状和端到端计算链。

## 3. 数据契约：先固定定义，再调整 SQL

配套设计建议首发统计正向词汇。所有函数应明确接收窗口、参考时间及必要上下文；数据库查询函数称为“只读查询”，不要把读取全局数据库和系统时钟的函数称为纯函数。

| 字段 | 建议定义 | 不得混用 |
|---|---|---|
| `window` | 周日学习日至周六学习日，真实边界下周日 04:00 | 滚动七天、未结束本周 |
| `activeDays` | 窗口内有效正向词汇作答日期的去重数 | 全 App 活跃天数、签到按钮次数 |
| `newWords` | 全部已知历史中第一次有效正向作答落在窗口内的不同词数 | 正向题总数、当前掌握数 |
| `reviewCount` | 窗口内有效正向作答数减当周首次作答词数 | 仅上周以前学过的老词数；本周新词的后续作答也算复习 |
| `studySeconds` | 窗口内词汇有效时长汇总，原始单位保留秒 | 页面打开时长；明细和汇总相加 |
| `streakAtEnd` | 从窗口末日向前连续有有效词汇作答的学习日数 | 今天的连续签到数 |
| `cumulativeDays` | 截至窗口末日的有效词汇作答日期并集 | 当前 `checkins` 全表计数 |
| `cumulativeWords` | 截至窗口末日已有首次有效正向作答的不同词数 | 当前 `progress.seen_count > 0` |
| `daily` | 七个学习日的明确分布，含零值日 | 只保留新增词日后推断整周规律 |
| `timeSlots` | 有效时间戳按已声明时区换算，记录样本覆盖率 | 声称单一时间戳携带原始旅行时区 |
| P4/P5 | 截至当周的事实和候选，最终结果写入快照 | 在回看时使用今天的 FSRS 状态重新判断 |

“有效作答”应复用现有记录与撤销、删除规则。同步去重沿用已有稳定事件身份 `sync_uid`，不能按秒级时间、词和方向拼接后去重。首次作答的可靠性依赖完整历史；导入缺历史时表述为“现有记录中的首次练习”，或省略相关推断，不把未知当成从未学过。

累计口径改用历史作答后，与主页基于 `progress` 的数字可能不同。应明确这是“截至该周的词汇作答记录”，不要为了对齐当前主页而把未来数据塞进旧周报。

## 4. 最小可靠快照

### 4.1 内容与身份

建议一周一份逻辑报告，本地表 `weekly_reports`；若现有数据库是共享账号容器，主键必须包括本地档案/账号范围和 `week_start`。即使目前一人一库，也要验证切换账号、匿名转登录、恢复备份时不会串读。

快照至少保存以下信息。可以将内容放进一个 JSON，不需要为每页建表：

- 身份：档案范围、窗口起止、报告 ID。
- 解释规则：`schemaVersion`、`rulesVersion`、词库内容版本、生成时区、`generatedAt`。
- 数据基准：生成时可见的同步水位/数据修订标识，以及历史是否完整；不要把本机水位当作全局版本比较。
- 展示内容：最终指标、关键词、参照物类别、P4、P5 词的稳定标识与展示文字、实际页面顺序。
- 修订信息：报告版本、必要的数据修正原因。

已读时间、提醒是否展示、待发通知 ID、上传重试次数属于交互或交付状态，和展示正文分开。尤其通知 ID、设备提示状态不能直接跨设备同步。

### 4.2 生成与修订规则

1. 完整周结束后，在库就绪、返回前台或合并完成的安全时机生成；正在答题时不抢占交互、不触发路由跳转。
2. 相同档案、窗口和数据版本的重复调用直接复用已有结果。React 重挂载、返回前台、网络重试都不能增加一份逻辑报告。
3. 未读草稿可以在补入历史后重算；已读报告不因今天的新记录或随机抽取改变。
4. 数据修正允许产生新版本，明确提示修正原因；普通规则升级不批量覆写旧报告。
5. 用户几周没打开时，先生成最近完整周，旧周按需补算或限量后台补算。不得在启动时同步扫描全部历史直至页面卡住。
6. 数据不足以还原的旧模块就省略；不能“补算”出当时不存在的历史掌握状态。

### 4.3 保存、导出与恢复

本地事务提交后，必须通过现有串行保存通道完成可靠落盘，再记录可提醒状态。正常保存保持安静；保存失败复用可靠的失败/恢复提示，不新增持续闪烁的“正在写入”。

**新增表必须显式覆盖以下路径：** 内存写入 → 本地增量 → 重启回放 → 整库快照 → 手动导出/恢复。仅执行 `CREATE TABLE` 并调用普通保存函数不能证明完成。

现有本地 delta 和云同步共享表清单。如果周报先只在本地保存，要明确扩展本地持久化表范围，或选择经过验证的整库持久化路径；不能为了让它落盘就随手加入云表清单，让“免费只存本地”失效。不要另建一整套通用存储框架。

新表迁移使用不存在则创建等幂等操作，保留旧版本可安全忽略的字段。损坏或未知未来格式只能影响该报告，不能阻止学习库打开；保留原始内容用于恢复，不静默清空。

## 5. 实施阶段与完成条件

工作量 S/M/L 仅表示相对复杂度。先按风险拆任务，再估人日；没有负责人、投入时间和设备清单时不编造具体完成日期。

| 阶段 | 交付物 | 依赖 | 完成条件 |
|---|---|---|---|
| 0 · 规则对齐（S） | 采用配套设计的决策表；建立统一数据口径 | 无 | 范围、门槛、周边界、免费历史、预测处理不再互相矛盾 |
| 1 · 分析修正与完整组装（M） | 修复历史锚点和累计；补 P4/P5、参照物全篇去重、3–6 页降级 | 0 | 三个原缺口反向复现转为正确结果；生产表形状和边界用例通过 |
| 2 · 本地快照闭环（M） | 幂等生成、可靠保存、恢复、旧周按需补算 | 1 | 生成后立即重启仍存在；重入不重复；损坏单份不拖垮应用 |
| 3 · 阅读闭环（M） | 可见入口、关闭、日期列表、按钮翻页、静态完整内容、P5 明确操作 | 2 | 离线可读、可退、可选周；阅读不改学习数据 |

| 5 · 站内提醒与本地通知（M） | 站内到期清理、一次性本地通知、深链、去重与取消 | 2、3 | 假时钟边界自动化 + iOS 真机验证；未生成不通知 |
| 6 · 分享（M） | 同快照长图、预览、系统分享与失败退路 | 3、4 的视觉定稿 | 中日文字、长词、缺页、取消、离线通过；无默认敏感明细 |
| 7 · 云端归档与权益（L） | 鉴权、同步冲突、历史恢复、到期/删号政策、权益矩阵 | 2 + 云业务规则 | 本地模拟、隔离账户及目标环境各有证据；免费与断订路径通过 |

阶段 1–3 构成一个可独立验收的基础发布包；完整规划仍包含阶段 4–8。若决定先发布基础版，应明确标为“基础阅读版”，不能说整套二楼、推送、分享和云端历史已经完成。

通知、分享和云端在接口与快照固定后可以独立开发；这只是依赖分析，不要求为此引入多个代理或新任务。

## 5.1 二楼交互实施补记（2026-09-12）

基础阅读闭环完成后，二楼交互补上了主页顶部下拉入口和可点击入口。主页仅在滚动到顶部且触摸起点位于顶部区域时响应下拉，避免把学习页或普通主页滚动误判成周报入口；点击入口始终可用。周报内部的横向滑动仍表示同一周期内翻页，垂直滑动表示切换更早或更新的周期，楼层牌显示周期楼层，页码单独显示。动效沿用现有 `data-motion` 三档，减弱或关闭时不播放下拉提示和页面入场动画。

这次补记不把物理 iOS 通知、真机手势、VoiceOver 和发布环境行为写成本地通过；这些仍按第 5、8 阶段的设备/发布闸门验收。

## 6. 云端方案：先复用，再决定是否增加索引

### 6.1 两条路径的选择

| 方案 | 适用条件 | 必须评估 |
|---|---|---|
| 放入现有账号快照 | 现有云权益和保存窗口已满足需求，小规模历史可随整库恢复 | 全量快照放大、旧客户端保留未知表、免费历史是否被意外上传 |
| 独立 R2 周报对象 | 需要按周读取、独立云权益或长期历史不随主快照膨胀 | 对象鉴权、按用户分页列出、版本冲突、删除与孤儿清理 |

若采用本稿“本地历史免费，Pro 云归档”的边界，独立 R2 对象更容易隔离权益；但云阶段才接入，不阻塞基础版。D1 索引不是必选：先测按用户前缀列出对象是否满足分页和排序，再决定要不要额外表。存储字节单价的比例不能单独决定架构。

### 6.2 独立对象的最小契约

- 服务端根据已验证会话确定 `user_id`，不相信请求体或路径传来的他人 ID。读、写、列出、删号均校验归属；云写和恢复按服务器权益判断。
- 一份逻辑报告按用户、周定位；同步时比较报告版本和内容摘要。相同内容重传是幂等成功，不能累计重复对象。
- 两端离线生成了不同内容时，不能“最后上传覆盖”。先取云端已接受版本；不同内容返回冲突状态，合并可用原始学习记录后生成明确修订。仅凭更大次数也不能证明数据更完整。
- 云端首次成功写入建立共享版本；各设备离线时允许暂存本地版本。同步前不承诺全设备已一致；修正已读内容时遵守可见修订规则，保留可恢复版本。
- 如果增加 D1 索引，R2 与 D1 不是一个事务：先保存可校验对象，再幂等写索引；失败可重试，并有遗漏索引/孤儿对象的对账修复。删除也必须可重试，不能删完索引就声称内容已删除。
- 429、断网和服务端失败进入有限重试并退避，不为了周报绕开现有安全限流；主学习同步优先。
- 服务端限制报告体积、支持的版本和每次分页量；学习统计不得成为购买授权依据。
- 旧 Web/iOS/小程序上传完整快照时不得擦掉独立云周报；恢复空设备的流程必须在旧端同步后再次验证。

### 6.3 账户与删除

匿名报告属于匿名本地档案，登录时不能自动混入当前账号；沿用项目既有、经过验证的数据合并交互。切账号立即切换可见历史，取消上一账号待发提醒。

删号需删除云对象、索引及其修订，防止旧设备队列重传复活。订阅到期不等于删号，不删除已下载本地报告。云保存期限、到期后保留期与重新订阅恢复范围必须在售卖之前填写并验证；禁止先承诺永久、以后再决定清理。

## 7. 成本模型修正

原稿的 23 GB 使用了 25% 生成资格率，因此不是“100 万用户全部每周生成”的最坏情况；600 B 也只是估计，不是包含所有实际中文、词条、版本信息后的测量结果。

统一使用十进制 GB，先忽略索引与对象元数据：

```text
报告数 = 用户数 × 云归档用户比例 × 该群体每周生成比例 × 保存周数
内容字节数 = 报告数 × 实测平均每份字节数
月写次数 ≈ 月新报告数 × (1 + 重试及修订系数)
月读次数 = 历史打开、预取、恢复、冲突核对与列表请求之和
```

“云归档用户比例”与“生成比例”可能相关，不能默认独立；付费群体通常应单独估计。用原稿的 600 B 假设，三年 156 周可得到：

| 示例假设 | 报告数 | 内容体积 |
|---|---:|---:|
| 100 万人全员每周生成 | 1.56 亿 | 93.6 GB |
| 100 万人，每周 25% 生成并上云 | 3900 万 | 23.4 GB |
| 100 万人，3% 为云用户，云用户每周全员生成 | 468 万 | 2.808 GB |
| 100 万人，3% 为云用户，其中每周 25% 生成 | 117 万 | 0.702 GB |

原稿按索引 30 B/行估算时，即使完全不计数据库开销，全员每周三年也为 **4.68 GB**，25% 场景为 **1.17 GB**，不能混写成 1.6 GB。实际用户 ID 长度、主键、索引与页开销必须用目标 schema 装载样本后测量。

截至核对日，R2 Standard 标价为 $0.015/GB·月，同时计 Class A/B 操作；D1 按读写行数计费，付费计划超出所含存储后为 $0.75/GB·月。二者的存储标价相差 50 倍，**总账单不会因此固定相差 50 倍**，还受免费量、取整、已有使用量、请求及其他服务影响。[R2 官方价格](https://developers.cloudflare.com/r2/pricing/)、[D1 官方价格](https://developers.cloudflare.com/d1/platform/pricing/)

上线前用完整快照测 p50/p95 大小，并代入真实计划。尤其要测周日集中生成和补历史的峰值，不能只用月均/日均请求声称“任何合理规模都不是瓶颈”。本次未读取云账号实际账单或当前剩余额度。

## 12. 技术复查补充（2026-09-11）

本节补充进一步沿真实写入、跨端往返和页面计时链路检查的结果。未修改应用代码，未访问真实学习库；除注明的隔离复现外，其余为源码确认或尚未接入时的风险，不能统称线上故障。

### T1 · 小程序会丢失周报依赖的答题时刻（已隔离复现，P0）

[`study-core.js`](../wechat-miniprogram/src/core/study-core.js) 的 `ensureStudySchema()` 没有补 `reviewed_at`，正反向写入也不带这个字段。[`sync-snapshot.js`](../wechat-miniprogram/src/runtime/sync-snapshot.js) 导入 `reviews` 时取两端列的交集；认识整张表，不代表能透传这张表里不认识的列。

在出厂种子库的内存副本上实际执行小程序建表、作答、导入一条带毫秒时刻的 v2 事件，再调用真实导出器：事件的 `sync_uid` 保留，但导出 `reviews` 没有 `reviewed_at` 列。若后续从这份备份恢复新设备，时段分析不能获得原时刻。原设备尚有完整事件不代表云端最新备份完整。

处理要求：小程序补列、补新事件写入，并保留收到的时刻；测试前端 → 小程序 → 导出 → 新设备恢复的字段值，不只检查行数或协议版本。历史 `created_at` 只有在格式和时区已验证时才可作为带来源标记的回填，不能一律当作等价毫秒时刻。

### T2 · 手动作答与“一键完成”没有可供周报使用的来源区分（源码确认，P0）

[`completeTodayWordPlan()`](../frontend/src/lib/word-api.ts) 会为整批词写入 `answer='know'`、`direction='forward'`、`schedulerMode='normal'` 的事件，与普通学习流水共享结构。周报只按日期、方向计数时，会把这一键操作纳入新词数、学习量和时段特征，可能选出“单日爆发”等标签。其他熟知标记事件也需要单独规定是否算有效学习。

这说明“有效作答”不能只写一句复用现有记录。若周报要描述实际逐题练习，应增加最小的事件来源标识，例如人工练习/批量完成/导入，或放弃对无法区分记录的行为推断。不能通过同一秒很多条之类猜测批量操作，会误伤合法数据。旧记录无可靠来源时，保留统计含义限制，不强行回填为人工练习。

### T3 · 现有时长不能精确拆出“仅正向词汇时长”（源码确认，P1）

[`WordStudy.tsx`](../frontend/src/pages/WordStudy.tsx) 的计时启用条件是 `card?.id`，没有按正向/反向区分；调用 `addWordStudySeconds(seconds)` 时也不传方向。按天、设备累计的表没有模式列。因此第 3 节数据契约中的“词汇有效时长”只能理解为当前计时器覆盖范围的累计，不能直接标成正向作答所花时间。

**本补充收紧首发要求：** 正向词汇次数可以单列，但在不能说明时长范围时省略时长模块；如保留，使用明确的现有范围标签。需要模式拆分时先改采集与合并主键，已有历史无法从日总数无损拆分，不按题数比例伪造精确时长。

### T4 · 时长按结算时的日期入账，跨 04:00 的区间没有拆分（源码确认，P1）

页面通常每 15 秒结算一次，`addWordStudySeconds()` 将整笔秒数交给 `recordStudySeconds(today(), seconds)`。例如 03:59:55–04:00:10 的 15 秒在 04:00:10 结算，会全记到新学习日，而不是前日 5 秒、新日 10 秒。延迟结算时也应按有效区间边界处理。

因此“原始事实精确到个位”不等于采集本身精确。周报若承诺严格周界，需要计时器保留可分割区间，在学习日边界结清，并覆盖周日跨周；仅更改周报查询无法修正已汇总的历史秒数。首发省略或近似展示时长时，要保留这个局限。

### T5 · 覆盖式二楼可能把阅读周报算成学习（接入风险，P1）

现有计时器监听 `document` 上的点击、滚动和触摸，启用依据仍有学习卡。如果未来周报只是覆盖在仍挂载的学习组件上，底层卡仍存在，阅读周报的操作可能继续激活学习计时。

目前周报 UI 尚未接入，不能称为已发生的 bug。接入时优先保证二楼只从主页进入；若需要覆盖当前会话，显式暂停计时、快捷键、自动读音和后台翻卡，关闭后恢复同一张卡与原状态。增加“打开周报 60 秒并交互，学习时长不增长”的集成用例。

### T6 · 通知点击路由没有现成闭环（源码确认，P1）

当前源码检索仅发现通知安排/取消等调用，没有 `localNotificationActionPerformed` 的处理。通知里的 `extra.target` 是数据，不能视为已经实现导航。本次未验证真机点击行为。

阶段 5 要新增并清理点击监听，使用报告 ID 与周标识定位；冷启动先等库和账户就绪，避免跳错账号或跳向空数据。热启动、冷启动、重复事件、报告已删除必须分别验收。

### T7 · 迁移执行顺序会影响新增表的追踪（接入风险，P1）

[`ensureSyncSchema()`](../frontend/src/lib/sync/schema.ts) 用 `WeakSet` 记住已经处理过的数据库实例，同一实例后续调用直接返回。若先初始化同步，再懒加载创建周报表，即使后来把它加入表清单，也不会自动补齐本实例的追踪列与触发器。

新表应在统一初始化阶段创建，或有明确的单表迁移入口；测试“同步已初始化后才创建表”的顺序。若选择周报本地整库保存路线，也不能把这个问题描述成云表追踪已完成。

### 已排除的一项泛化判断

不能未经检查就断言首次词查询“一定全表扫描、必须新增索引”。本次读取出厂库结构发现已有 `idx_reviews_day_word`、`idx_reviews_word_day`，实际 `EXPLAIN QUERY PLAN` 显示窗口查询和历史子查询均使用对应索引。仍需大样本性能实测，但目前没有证据要求为了周报再加重复索引；也没有测得可报告的真机耗时。

## 14 · 最终拍板与二次验收（2026-09-12）

本节记录产品负责人在实现前后的最终决定，**覆盖本文前面仍标为“建议”或“待采用”的冲突项**，尤其是正向词汇首发、04:00 周界、16:00 提醒和本机历史免费等早期建议。后续开发与验收统一按以下口径：

- 周报从主页进入。通知在背单词时被点击也会卸载当前学习页并进入周报；关闭周报直接回主页，因此阅读周报不会继续累计学习时长。

## 16 · 视觉与动效重做（2026-09-12）

起因：技术上可用，但周报页的配色、字号层级、版式编排和动效都不合格（原实现几乎没有动效，且整页是写死的浅紫，深色模式下会发白）。

### 16.1 采用的技术结论

参考公开的动画性能指南与视图过渡/滚动驱动动画资料，本轮只采纳其中**不依赖新 API、且不吃性能**的部分：

- **只动 `transform` 和 `opacity`**：这两个属性只走合成器，不触发 layout/paint；`width/height/top/left/box-shadow/background-color` 一律不做动画（阴影改用伪元素透明度的手法不需要，本轮不做阴影动画）。
- **进度/柱状用 `scaleX`/`scaleY` + `transform-origin`**，而不是动画 `width`/`height`。
- **`animation-fill-mode: both` + `ease-out`**，入场不会闪一下首帧。
- **`will-change` 不用**：本页动画都是短时一次性，提升合成层反而白占 GPU 内存。
- **View Transitions API 与滚动驱动动画暂不采用**：iOS 16.4 起才有部分支持，本工程部署目标为 16.4，且需要在 WebView 内验证；先用手写 CSS 达到同等效果，避免引入需要能力检测的分支。

### 16.2 落地内容

- **局部设计 token**：颜色、圆角、缓动、阴影都收敛到 `.weekly-report-page` 上的 `--wr-*`，浅色与深色各一套；页面内不再出现写死的十六进制颜色。
- **深色模式**：补齐 `[data-theme="dark"]` 一套，深色下不再发白。
- **字号层级**：kicker / 标题 / 正文 / 数字各有固定档位；数字统一 `font-variant-numeric: tabular-nums`，滚动时宽度不跳。
- **版式**：封面加七天日期条；统计从「盒子套盒子」改为细线分隔的账本；模式占比改成一条堆叠条 + 图例；高光改成引文式；疑难词改成卡片列表。每页垂直居中，内容短也不会顶在上边留一大片空。
- **动效**：换页/换周方向感入场、子元素按 `--i` 交错上浮、封面柔光缓慢漂移、柱状与占比条生长、日期点弹入、按钮按压缩放。
- **降级**：`prefers-reduced-motion: reduce` 与 `[data-motion="reduced"|"off"]` 下全部停止，且**内容一步到位、一个数字都不少显示**（已用静态预览在 `data-motion="off"` 下核对）。
- **回归修复**：入场位移从 18px 收到 10px —— 18px 会把内容顶出视口，窄屏上闪出一条横向滚动条（预览实测 `scrollWidth` 比 `innerWidth` 多 3px）。

### 16.3 分享长图同步重做

页面换了视觉之后，`weekly-report-share.ts` 里的长图还是旧配色（写死的 `#7046A6`）和旧版式，分享出去和用户刚看过的页面是两套东西。本轮把长图一并重做：

- 配色改为与 `.weekly-report-page` 浅色 token 同值；版式也照页面走：kicker + 区间 + 衬线标题 + 大数字 + 七天日期条 + 细线账本 + 柱状图 + 高光引文 + 模式堆叠条 + 页脚。
- **仍然不带易错词明细**：计划要求 P5 选词只留在 App 内，分享图里不出现「你哪些词记不住」。
- 高度按实际内容算：没有高光就不画那一块，短报告不留大片空白；时长不足一分钟写「不足 1 分钟」。
- 逐字断行，长关键词（如「匀速前进中的常来常往者」）会换行而不会溢出。

### 16.4 验证方式与边界

用与组件一致的 DOM + 真实 `app.css` 做静态预览，在无头 Chrome 下按 500px 视口截图核对浅色、深色与关动效三种状态，并测量 `scrollWidth` 确认无横向溢出；长图则用 esbuild 把模块单独打包后在浏览器里真实渲染，覆盖完整报告、短报告、长关键词三种输入。

⚠️ **`npx cap copy ios` 在本仓库会非常慢甚至像卡住**：`dist/` 有 3.3 万个文件（主要是 `audio`），复制过程没有输出。推荐直接 `rsync -a --delete dist/ ios/App/App/public/`（该目录已被 `ios/.gitignore` 忽略，属生成物）。注意 `cap copy` 会先清空目标目录，中途中断会留下**不完整的 public**，App 会白屏 —— 中断后必须重新同步一次。

⚠️ **在受限环境里这种批量复制会被中途杀掉**：本轮实测 `rsync` / `cp -R` / 逐文件脚本都会在复制到一万多个文件时收到 SIGTERM，结果是「命令返回成功、但目标目录少了一批文件」。此时 Xcode 会报
`error: The file “xxx.aac” couldn’t be opened because there is no such file`，而那个文件其实在源目录里存在 —— 它只是在复制时被跳过了。判断方法：比较两边文件数
（`find dist -type f | wc -l` 与 `find ios/App/App/public -type f | wc -l`）。**在正常终端里跑一次 `npx cap copy ios` 即可恢复**；不要靠反复重试增量补齐，容易误判为源码问题。

⚠️ 本轮改了 `app.css` / `WeeklyReportPage.tsx` 之后重新构建过 `dist/`，因此 `ios/App/App/public` 又落后于最新构建；**任何真机/模拟器验证或打包前都要先重新同步一次**。

以上只证明视觉、降级与长图渲染正确，**不代表真机手势、VoiceOver、低端机帧率已验收**，这些仍按第 5、8 阶段闸门执行。
